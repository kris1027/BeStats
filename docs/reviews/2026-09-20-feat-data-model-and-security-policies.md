## Summary

This change lands spec 0001's three user-tracking tables (`user_movie_state`, `user_show_state`, `user_episode_state`), the two enum types, the timestamp-maintenance triggers, twelve RLS policies, generated TypeScript types, and a thorough pgTAP suite (four files, 84 assertions) plus two Vitest guards for the type shape and the service-role boundary. The SQL is careful and well commented — the hand-corrected grant/revoke section in the migration in particular documents a real Supabase gotcha (default privileges silently handing `anon`/`authenticated` more than intended) and the pgTAP suite proves it behaviourally, not just by inspection. The main problems are two coverage gaps in the very mechanisms meant to lock in AC-4 and AC-15 going forward: the declarative schema file doesn't carry the same privilege fix the migration hand-applies, and the new service-role regression test (plus its documented manual-grep counterpart) never scans the repo-root application files, including the one file (`proxy.ts`) that already wires up a Supabase client on every request.

## Major

### 🟠 Schema file omits the `authenticated` privilege fix the migration hand-applies, `supabase/schemas/04-policies.sql:33-39`
**Problem**: The committed migration (`supabase/migrations/20260920174608_user_tracking_schema_and_rls.sql:916-926`) revokes ALL privileges from `authenticated` before re-granting exactly `SELECT, INSERT, UPDATE, DELETE`, with a comment explaining that Supabase's default privileges hand `authenticated` `MAINTAIN, REFERENCES, TRIGGER, TRUNCATE` too (`TRUNCATE` bypassing RLS entirely). But `supabase/schemas/04-policies.sql`, the declarative source of truth the build plan says future migrations are diffed from, only does `revoke all ... from anon, public` and then `grant select, insert, update, delete ... to authenticated` — it never revokes the pre-existing default-privilege grant from `authenticated` first. The schema file and the migration it supposedly produces have diverged.
**Why it matters**: The next schema change (e.g. adding a column) will run `supabase db diff` against these schema files. Because the file never states "revoke everything from authenticated first," the regenerated migration has no reason to re-emit that revoke, and the excess default-privilege grants (most importantly `TRUNCATE`, which empties a table without going through row level security at all) can silently reappear for `authenticated`. The pgTAP assertion in `020-security-configuration.test.sql` ("authenticated holds nothing beyond select, insert, update and delete") only proves the *current* migrated state; it does not protect the *next* one, because the file it would be regenerated from is missing the fix.
**Suggested fix**: Add `revoke all on table public.user_movie_state, public.user_show_state, public.user_episode_state from authenticated;` immediately before the three `grant select, insert, update, delete ... to authenticated` lines in `04-policies.sql`, mirroring what the migration already does, and add a comment cross-referencing the migration's explanation so the next person editing this file doesn't quietly drop it again.
**Resolved**: `supabase/schemas/04-policies.sql:37-44` now revokes all privileges from `authenticated` on all three tables before the four-command grant, with a comment naming the `TRUNCATE` risk, and the file's closing caveat covers the `authenticated` case as well as `anon`. `supabase db schema declarative sync --no-apply` reports no schema changes and emits no migration, so the added revokes introduce no drift. The live database was already correct via the migration's hand correction; this closes the source-of-truth gap for the next regeneration.

### 🟠 The service-role regression test (and its documented manual check) never scans repo-root application files, `security-boundary.test.ts:14-16`
**Problem**: `SCANNED_DIRS = ["app", "lib", "scripts"]` and `SCANNED_FILES = [".env.example"]`. Repo-root TypeScript files — `proxy.ts`, `next.config.ts`, and any future root-level module — are not under any of those directories, so they are never read by `offenders()`. `proxy.ts` already exists, already imports `createServerClient` and `getPublicEnv`, and runs on every request (per its own docstring, it "refreshes the Supabase session"). It is exactly the kind of file where a future change (e.g. an auth check added to middleware) could plausibly introduce an elevated client. The same blind spot is baked into the documented manual check in `verify.md:118`: `git grep -n -iE "service_role|sb_secret" -- lib app scripts .env.example` — the exact same path list, the exact same gap.
**Why it matters**: AC-15 requires the service role key to appear "nowhere in application code," and this test's own docstring says its purpose is to catch a leak "long after anyone thinks to run the grep again." Right now `proxy.ts` is clean, so there's no active leak — but the guard that's supposed to make that permanent doesn't actually cover the file most likely to accumulate server-side auth logic as the project grows (middleware, and later `components/`, are both plausible future homes for a mistake this test would miss).
**Suggested fix**: Scan repo-root `.ts`/`.mjs` files (e.g. via `readdirSync(".")` filtered to files, not just the three subdirectories) in addition to the existing directories, or explicitly add `proxy.ts` and `next.config.ts` to `SCANNED_FILES`. Update the `verify.md` grep command to match the same file set so the automated and manual checks stay in sync.
**Resolved**: `security-boundary.test.ts` gained a `rootFiles()` helper that scans repo-root files with the scannable extensions, folded into a shared `scannedPaths()` used by both needle checks, plus a new test asserting `proxy.ts` is in the scanned set so the hole cannot reopen in silence. The `.test.tsx` exclusion was added alongside `.test.ts`. `verify.md:17` now carries matching root globs, so the manual grep and the automated guard cover the same file set.

## Strengths

- The pgTAP suite is unusually rigorous about proving *why* a check works rather than just that it passes: `030-cross-user-isolation.test.sql` explicitly notes why the cross-user proof must be re-checked after `reset role` rather than from inside user A's session (otherwise it would be a tautology), and it includes a no-subject-claim test to rule out a predicate that treats a missing JWT subject as a match.
- The migration's hand-correction comment (`supabase/migrations/...sql:894-914`) is an excellent piece of institutional memory: it names the exact Supabase default-privilege trap, cites which two problems it fixes, and explains why `postgres`/`service_role` keep the broader grants. This is the kind of comment that saves the next engineer from re-discovering the same gotcha the hard way.
- Plan counts in every pgTAP file match the actual assertion count exactly (verified by hand for all four files), so there's no silently-dropped assertion.
- `database.types.test.ts` asserts the *shape* of the generated enums (not widened to `string`) with no database needed, which is a genuinely useful complement to `db:types:check`'s live-drift check — one runs in CI with no Supabase reachable, the other proves the file matches a running instance.
