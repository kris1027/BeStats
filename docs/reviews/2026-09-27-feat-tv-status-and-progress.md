## Summary
This lands spec 0013: one status per show written only through `set_show_status` / `remove_show_status` / `restore_show_status`, an automatic Watching move folded into the three episode functions via `start_watching_show`, a pure `showProgress` rule, and a merged movie+show watchlist behind a `security_invoker` view. The SQL is careful and well guarded (row locking before reporting "previous" values, `on conflict ... where` used correctly to make the automatic move idempotent and status-safe, empty `search_path` and revoke/grant pairs on every new function, a real transaction-local flag rather than a client-writable column for the Undo backdoor into the `listed_at` trigger). pgTAP coverage of the three status functions, the automatic-Watching matrix, and the view is thorough and specifically targets the cross-user and Undo-expiry edges. The two issues below are both real but narrow: neither is a security hole or a data-loss path, so this is approvable with the fixes taken as follow-ups.

## Minor
### 🟡 A stale client can flip `status_source` from `system` to `user`, undetected, `supabase/schemas/05-functions.sql:` `set_show_status`
**Problem**: AC-2 states "so a `system` status never silently turns into a `user` one," but the guard for "choosing the status the show already has" lives only in `ShowStatusControl.choose()` (`components/tracking/show-status-control.tsx:79`, `if (shown?.status === status) return;`), which compares against that tab's own optimistic state. `set_show_status` itself always writes `status_source = 'user'` on any call, with no check that the target already equals the current status. If a show is auto-moved to Watching in one tab (or by another action) while a second tab still shows a stale "Want to Watch"/"Watching" pill, picking the status the row already effectively holds in that second tab sends a live `setShowStatus` call and silently converts the row from `system` to `user` sourced.
**Why it matters**: `status_source` is the field feature 16 (automatic completion) will use to tell a deliberate choice from an automatic one; a value that can flip without the user intending a change undermines that distinction, and the failure is silent (no error, no rollback, nothing visibly wrong for the user to notice or undo).
**Suggested fix**: Have `set_show_status` no-op (or at least keep `status_source` unchanged) when `p_status` already equals the stored status, mirroring the client guard server-side, or return the current row unchanged with `previous_* = null` in that case so no source flip is possible regardless of which tab or client sent the request.

### 🟡 Progress line disappears rather than showing "unavailable" when only the status read fails, `components/tracking/show-progress-slot.tsx:36-45`
**Problem**: `ShowProgressSlot` explicitly handles `watched.kind === "failed"` (shows the Unavailable panel), but when `getShowStatus` alone returns `{ kind: "failed" }` (a DB error) while the watched-ids read succeeds, `hasRow` becomes `false` (since `status.kind !== "ok"`), and if the user also has zero watched regular episodes for that show, the function falls through to `if (!hasRow && watchedIds.size === 0) return null;` — hiding the line entirely instead of reporting a failure.
**Why it matters**: A user who has a status row (e.g. freshly set to Watching, no episodes marked yet) but hits a transient status-read error would see no progress line at all with no retry affordance, rather than the "Progress unavailable right now" state AC-11 intends for read failures.
**Suggested fix**: Treat `status.kind === "failed"` the same as `watched.kind === "failed"` — render `<Unavailable retryHref={retry} />` before computing `hasRow`, rather than letting it fall through to the visibility heuristic.

## Nits
- ⚪ `supabase/migrations/20260926120000_show_status_functions.sql:` (`restore_show_status`), the leading guard `p_status is null or p_source is null or p_listed_at > now()` treats a null `p_listed_at` as passing (SQL `NULL > now()` is unknown, so the `IF` doesn't fire). This can't be reached through the current action/Zod path (a listed removed row always carries a non-null `listed_at` by the table's own check constraint), but a direct RPC call with a mismatched `p_status`/`p_listed_at` pair would surface as a raw `23514` constraint violation instead of the clean `P0002` "undo expired" every other malformed Undo gets. Own-row only, so not a security issue — just a rougher error path than the rest of the function.
- ⚪ `supabase/migrations/20260926120100_start_watching_show.sql:` (`mark_episode_watched`, `rate_episode`), the `prior` CTE reads `watched_at` from a plain `select`, not `select ... for update`. Under two genuinely concurrent calls for the same user/episode (double-submit, two tabs), both could read "not yet watched" from their own snapshot and both report `show_started = true`, producing a duplicate "moved to Watching" toast even though only one call's write actually took effect (the episode data itself stays correct via the ON CONFLICT's own row lock). Cosmetic, same-user only, and requires a genuine race to trigger.

## Strengths
- The Undo design in SQL is a standout: `restore_show_status`'s `p_expected null` vs. set branches map exactly to the removal/Stop-watching cases, the 10-minute windows are enforced server-side against `updated_at`/`removed_at` rather than trusted client math, and the `bestats.restore_listed_at` transaction-local setting is a clean way to let one trigger serve both the normal stamping path and the Undo path without giving PostgREST any way to set `listed_at` directly.
- `showProgress` in `lib/tv/progress.ts` is a tight, well-tested pure function (duplicate TMDB ids, malformed dates, watched-but-since-delisted episodes, and the `none_aired` vs. zero distinction are all covered), and it's reused unchanged by both the hero progress line and the watchlist's Next episode pill exactly as the spec's Follow-up section anticipates for features 15/16.
