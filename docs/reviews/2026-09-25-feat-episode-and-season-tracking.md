## Summary

Spec 0011 adds the episode/season Watched and score pills to `/shows/{id}/season/{n}`, backed by five new `SECURITY INVOKER` Postgres functions (mark, rate, mark-season, unmark-season, restore), four new Server Actions in `app/shows/actions.ts`, a season-scoped `useOptimistic` client store, and two pure domain modules (`lib/tv/air-status.ts`, `lib/tv/season-watch.ts`) that keep the UTC "today" comparison out of the TMDB `use cache` scope. The design mirrors spec 0007's movie tracking pattern closely and extends it correctly: idempotent target-value writes, `on conflict ... where` used precisely so an already-watched episode is silently skipped and left out of `returning`, ratings and watched state kept independent in every write path, grants revoked from `anon`/`PUBLIC`/`authenticated` and re-granted to `authenticated` only, and the declarative schema file kept byte-identical with the hand-written migrations. I traced the SQL against the pgTAP suite, the TypeScript optimistic reducer (`applyEpisodeIntent`) against the same cases, the Server Actions' error mapping and TMDB-confirmation order, and the season page's Suspense wiring for the one-query-per-render requirement (AC-18), and found no correctness or security defects.

I ran the real checks rather than trusting the spec's claims: `pnpm typecheck` (clean), `pnpm lint` (clean, Biome), `pnpm test` (1161/1161 passed), `pnpm build` (`/shows/[id]/season/[number]` renders as ◐ Partial Prerender, confirming AC-20), `pnpm db:types:check` (committed types match the local schema), and `supabase db diff` (no drift between the declarative schema and the generated migrations). `pnpm test:db` failed on my machine on an *unrelated, pre-existing* file — see the Minor finding below; the new `080-episode-tracking-functions.test.sql` itself passed all 54 assertions cleanly, including the cross-user (AC-19), idempotency (AC-9, AC-16), and `user_show_state` isolation (AC-24) cases.

## Minor

**Problem**: Running `pnpm test:db` on this branch fails one assertion in `040-write-semantics.test.sql` ("marking a season watched twice still leaves one row per episode": have 7, want 3). I traced it: the local Supabase database (used for both `pnpm dev:docker` and `supabase test db`) already holds committed rows for user A, show 1396 (`Breaking Bad`), season 1, episodes 62085–62091 and two season-0 rows, all timestamped today — clearly left over from manually walking through `verify.md`'s UI steps against the same show id `040` uses as its own fixture. `040` was not touched by this PR and is not a regression; the new `080` file passes cleanly on its own (54/54), and CI starts a fresh Supabase stack per run (`.github/workflows/checks.yml`), so this specific failure won't reach CI.
**Why it matters**: AGENTS.md section 13 says to report actual check results and never claim a check passed without running it, and `docs/scope/scope.md` already marks "Test it" done for this feature. As it stands, anyone who runs the documented manual verify steps against the local stack and then runs `pnpm test:db` without resetting will see an unrelated pgTAP file fail and may waste time chasing a phantom regression in the new code.
**Suggested fix**: Run `supabase db reset` (or note the requirement in `verify.md`'s Commands section) before the final `pnpm test:db` pass, so the check is confirmed green from a clean database, not just from the new file's own suite.

### 🟡 `verify.md` leaves one manual step unchecked while scope.md marks verification done, `docs/specs/0011-episode-and-season-tracking/verify.md:38`
**Problem**: `docs/scope/scope.md` marks "Verify it: `/check verify episode and season tracking`" as done, but `verify.md`'s "Value sourcing checks" leaves one box open: `- [ ] "Today": with the server clock just before and just after UTC midnight, an episode dated the new day flips from Upcoming to markable exactly at 00:00 UTC, not local midnight`.

The behavior is thoroughly covered by unit tests (`lib/tv/air-status.test.ts`'s "the UTC midnight boundary" block), so there's no functional risk, but the unchecked manual step means the *live*, server-clock version of this check was not actually run, which the scope row's checkmark implies.
**Suggested fix**: Either run the live check (adjust the server or a test show's air date around a real UTC midnight) and tick the box, or leave the scope.md line open until `verify.md` is fully green, so the two documents agree.

## Nits

- ⚪ `lib/tv/air-status.ts:38`, `if (parseTmdbDate(airDate) === null || airDate === null) return "unknown";` — the second half is dead: `parseTmdbDate(null)` already returns `null`, so the first condition always catches a `null` `airDate`. Harmless, but reads as if `null` needed separate handling.

## Strengths

- The conditional writes are exactly as tight as spec 0007's: `mark_episode_watched`/`rate_episode` use `on conflict ... set watched_at = coalesce(s.watched_at, now())`, and `mark_season_watched`'s `on conflict do update ... where s.watched_at is null` relies on documented Postgres behavior (a suppressed conflict row is silently excluded from `returning`) to report exactly the newly-marked ids — confirmed both by pgTAP (`array[930103, 930104]` back from a call that also includes two already-watched ids) and by `airedEpisodesForMarking`'s matching dedup rule in TypeScript.
- The optimistic UI is built on a single, well-reasoned trick: `useOptimistic([], reducer)` with a constant `[]` base rather than a real prop, so the pending-intents overlay always reverts to nothing once a transition settles, letting the server's `refresh()`-delivered props be the sole source of truth on both success and rollback (AC-13). The accompanying `season-tracking.test.tsx` suite actually exercises this with deferred promises settled by hand, asserting mid-flight optimistic state and post-rollback state separately.
- Real, not simulated, verification: typecheck, lint, the full vitest suite, a production build, `db:types:check`, and `db diff` were all run by me on this branch and passed cleanly; the new pgTAP file's 54 assertions (grants, invoker rights, idempotency, duplicate-id handling, the three list guards, restore bounds, and full cross-user isolation) passed as well.
